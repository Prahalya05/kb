# Lesson A2 — The stack up close: calling conventions, frames, assembly and stack smashing

> Level: advanced. Prerequisites: B3 (call stack), B6 (memory layout), I5 (object files), I7 (GDB). Time: about 3 hours.
> Platform: x86-64 Linux, System V AMD64 ABI. Assembly generated by GCC 13.3 (Ubuntu 24.04 build), November 2026, with `-fno-asynchronous-unwind-tables -fcf-protection=none` to remove directive noise unless stated otherwise.

---

## 1. Why this lesson exists

"The stack" has been a diagram so far. Now we look at the real thing — the machine instructions GCC emits for a function call — because:

- Debuggers, profilers, crash dumps and sanitizers all *walk stack frames*; you need to read what they show.
- Performance: knowing that the first six integer arguments travel in registers explains why small functions are cheap and why passing big structs by value is not.
- Security: the classic stack buffer overflow overwrites a **return address** stored next to local buffers. Defences (stack canaries, non-executable stacks, shadow stacks) only make sense once you see the layout.
- Interoperability: the **calling convention** (ABI) is the contract that lets C call assembly, Rust, Fortran, or a JIT — and lets Python's `ctypes` call C.

---

## 2. Intuition: a relay race with a fixed baton protocol

Each function call is a relay hand-off with strict rules agreed in advance (the ABI):

- The first six baton items (integer/pointer arguments) are passed **hand to hand** in registers `rdi, rsi, rdx, rcx, r8, r9`; extra ones are left **on the track** (the stack).
- The runner who calls (`call`) leaves a note on the track saying "come back to me here" — the **return address**.
- Some lockers (callee-saved registers) must be returned exactly as found; others (caller-saved) may be trashed by the callee.
- The result comes back in `rax`.

Overflowing a local buffer is like scribbling past your notebook's last page onto the "come back here" note — then the runner returns to wherever the scribble points.

---

## 3. Precise definitions (System V AMD64 ABI, as summarised by Harvard CS61 and OSDev)

- **Argument registers:** "the first six function arguments are passed in registers `%rdi, %rsi, %rdx, %rcx, %r8, and %r9`, respectively"; floating-point arguments go in `%xmm0`–`%xmm7`; remaining arguments are pushed on the stack (right to left).
- **Return value:** in `%rax` (and `%rdx` for 128-bit), floating-point in `%xmm0`.
- **Callee-saved registers:** `%rbp, %rbx, %r12, %r13, %r14, %r15` (and `%rsp`); all other general-purpose registers are caller-saved.
- **Stack alignment:** "when a `callq` instruction begins execution, the `%rsp` register must be 16-byte aligned".
- **Red zone:** the 128 bytes below `%rsp` that signal handlers will not clobber, so **leaf functions** (which call nothing) may use them without moving `%rsp` (OSDev *System V ABI*).
- **`call` / `ret`:** `call f` pushes the address of the next instruction and jumps to `f`; `ret` pops that address into `%rip`.
- **Frame pointer:** at `-O0`, GCC sets up `%rbp` as a fixed base for the frame (`push %rbp; mov %rsp, %rbp`); with optimisation it is usually omitted (`-fomit-frame-pointer` is enabled at `-O1` and above — `gcc -Q --help=optimizers -O1` reports it `[enabled]` on the test machine), which is why profilers ask for `-fno-omit-frame-pointer`.
- **Stack protector:** `-fstack-protector` "emit[s] extra code to check for buffer overflows, such as stack smashing attacks"; `-fstack-protector-strong` protects more functions (GCC *Instrumentation Options*). Ubuntu's GCC enables `-fstack-protector-strong` and `-fcf-protection=full` **by default** (observed on the test machine with `gcc -Q --help=common`).

The official ABI document is maintained in the `x86-64-ABI` repository of the *x86 psABIs* group on GitLab (see Sources).

## 4. Step by step

### Step 1 — a call with seven arguments at `-O0`

```c
// file: frame.c
// build: gcc -std=c17 -O0 -fno-asynchronous-unwind-tables -fcf-protection=none -S -o frame_O0.s frame.c && gcc -std=c17 -O2 -fno-asynchronous-unwind-tables -fcf-protection=none -S -o frame_O2.s frame.c
// run: grep -v -E '^\s*\.(file|text|globl|type|size|ident|section|p2align)' frame_O0.s; echo =====; grep -v -E '^\s*\.(file|text|globl|type|size|ident|section|p2align)' frame_O2.s

// seven integer arguments: six travel in registers, the seventh on the stack
long sum7(long a, long b, long c, long d, long e, long f, long g)
{
    long local = a + b + c + d + e + f + g;
    return local * 2;
}

long caller(void)
{
    return sum7(1, 2, 3, 4, 5, 6, 7);
}
```

`-O0` output (annotated with `;` comments added by hand):

```text
sum7:
	pushq	%rbp              ; save caller's frame pointer (callee-saved)
	movq	%rsp, %rbp        ; our frame base
	movq	%rdi, -24(%rbp)   ; spill a..f from registers into the frame
	movq	%rsi, -32(%rbp)
	movq	%rdx, -40(%rbp)
	movq	%rcx, -48(%rbp)
	movq	%r8, -56(%rbp)
	movq	%r9, -64(%rbp)
	movq	-24(%rbp), %rdx
	movq	-32(%rbp), %rax
	addq	%rax, %rdx
	...                       ; (adds c, d, e, f the same way)
	movq	16(%rbp), %rax    ; g: the 7th argument, ABOVE the return address
	addq	%rdx, %rax
	movq	%rax, -8(%rbp)    ; local
	movq	-8(%rbp), %rax
	addq	%rax, %rax        ; local * 2 -> rax (return value)
	popq	%rbp              ; restore caller's frame pointer
	ret                       ; pop return address into rip
caller:
	pushq	%rbp
	movq	%rsp, %rbp
	pushq	$7                ; 7th argument goes on the stack
	movl	$6, %r9d          ; arguments 6..1 in registers
	movl	$5, %r8d
	movl	$4, %ecx
	movl	$3, %edx
	movl	$2, %esi
	movl	$1, %edi
	call	sum7              ; pushes return address, jumps
	addq	$8, %rsp          ; caller removes its stack argument
	leave
	ret
```

Three things to notice:

1. **`16(%rbp)` is `g`**: above `%rbp` sit the saved `%rbp` (at `0(%rbp)`), the return address (at `8(%rbp)`), then the stack arguments.
2. **`sum7` never subtracts from `%rsp`**, yet stores at `-64(%rbp)`. It is a leaf function, so it uses the **red zone** below `%rsp`.
3. Writing to `movl $1, %edi` sets the full `%rdi` — on x86-64, writing a 32-bit register zero-extends into the 64-bit register, which is why the compiler uses the shorter instruction.

`-O2` output:

```text
sum7:
	addq	%rsi, %rdi
	addq	%rdx, %rdi
	addq	%rcx, %rdi
	addq	%r8, %rdi
	addq	%r9, %rdi
	addq	8(%rsp), %rdi     ; g: just above the return address (no frame pointer now)
	leaq	(%rdi,%rdi), %rax ; rax = 2 * rdi  (lea as arithmetic)
	ret
caller:
	movl	$56, %eax         ; (1+...+7)*2 computed at compile time
	ret
```

No frame pointer, no spills, and `caller` became a constant: the optimiser inlined `sum7` and folded the arithmetic. This is why debugging `-O2` code is hard (lesson I7) and why "function call overhead" is often zero in practice.

### Step 2 — watch the stack grow downward

```c
// file: depth.c
// build: gcc -std=c17 -O0 -Wall -Wextra -o depth depth.c
// run: ./depth

#include <stdio.h>
#include <stdint.h>

// prints where each recursive call's local lives, and the distance to the previous frame
void dive(int depth, uintptr_t prev)
{
    int marker = depth;
    uintptr_t here = (uintptr_t)&marker;          // integer form of the address, for arithmetic
    if (prev)
        printf("depth %d: &marker=%#lx  (%ld bytes below previous frame)\n",
               depth, (unsigned long)here, (long)(prev - here));
    else
        printf("depth %d: &marker=%#lx\n", depth, (unsigned long)here);
    if (depth < 3)
        dive(depth + 1, here);
}

int main(void)
{
    dive(0, 0);
    return 0;
}
```

Output (addresses vary with ASLR; the distances do not):

```text
depth 0: &marker=0x7ffcb1bfd16c
depth 1: &marker=0x7ffcb1bfd12c  (64 bytes below previous frame)
depth 2: &marker=0x7ffcb1bfd0ec  (64 bytes below previous frame)
depth 3: &marker=0x7ffcb1bfd0ac  (64 bytes below previous frame)
```

Each call costs 64 bytes of stack here (return address + saved `%rbp` + locals + spilled arguments + padding to keep 16-byte alignment). With an 8 MiB stack, that bounds the recursion depth of this function to roughly 8 MiB / 64 B ≈ 131,000 frames — the reason deep recursion crashes.

### Step 3 — stack smashing, and the canary that catches it

```c
// file: smash.c
// build: gcc -std=c17 -O0 -fstack-protector-strong -o smash smash.c && gcc -std=c17 -O0 -fno-stack-protector -o smash_np smash.c
// run: ./smash Prahalya; ./smash AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA; echo "exit=$?"; ./smash_np AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA; echo "exit=$?"

#include <stdio.h>
#include <string.h>

// copies an attacker-controlled string into a 16-byte stack buffer: classic overflow
void greet(const char *name)
{
    char buf[16];
    strcpy(buf, name);            // no length check
    printf("hello %s\n", buf);
}

int main(int argc, char *argv[])
{
    greet(argc > 1 ? argv[1] : "world");
    return 0;
}
```

Output (stdout was a pipe, so the `hello AAAA…` lines of the two overflowing runs were still in the stdio buffer when the process died — lesson I7's buffering effect; in a terminal you would also see them):

```text
hello Prahalya
*** stack smashing detected ***: terminated
Aborted
exit=134
Segmentation fault
exit=139
```

- With the protector, GCC placed a secret random value (the **canary**) between `buf` and the saved registers/return address. In the assembly you can see it loaded from thread-local storage at function entry and checked at exit:

  ```text
  movq	%fs:40, %rax           ; load the canary
  ...
  subq	%fs:40, %rax           ; compare with the value still on the stack
  call	__stack_chk_fail@PLT   ; mismatch -> abort
  ```

  The 40 `A`s overwrote the canary on their way to the return address, so the check aborted *before* `ret` could jump to `0x4141414141414141`.
- Without the protector, `ret` popped the overwritten return address and jumped into garbage: segmentation fault. In an exploit, the attacker chooses those bytes.
- The `endbr64` instructions you saw in earlier lessons come from `-fcf-protection` (Intel CET indirect-branch tracking), another default hardening on Ubuntu's GCC.

### Step 4 — reading frames in GDB

```bash
gcc -std=c17 -O0 -g -o depth depth.c
gdb -q -batch -ex 'break dive if depth == 2' -ex run -ex 'info frame' -ex 'x/2gx $rbp' ./depth
```

Output on the test machine:

```text
Breakpoint 1, dive (depth=2, prev=140737488317516) at depth.c:10
Stack level 0, frame at 0x7fffffff6c30:
 rip = 0x55555555517c in dive (depth.c:10); saved rip = 0x555555555201
 called by frame at 0x7fffffff6c70
 Saved registers:
  rbp at 0x7fffffff6c20, rip at 0x7fffffff6c28
0x7fffffff6c20:	0x00007fffffff6c60	0x0000555555555201
```

The saved `rbp` sits at `0x…6c20` and the saved `rip` (return address `0x555555555201`, an address inside the caller) right above it at `0x…6c28`; `x/2gx $rbp` shows those two words — the exact layout of the diagram below. The two frames are 0x40 = 64 bytes apart (`0x…6c70 − 0x…6c30`), matching Step 2.

## 5. Diagrams

Frame layout for `sum7` at `-O0` (addresses grow upward in this picture):

```text
 higher addresses
 +--------------------------+
 | 7th argument g = 7       |  16(%rbp)   <- pushed by caller
 +--------------------------+
 | return address           |   8(%rbp)   <- pushed by `call`
 +--------------------------+
 | saved %rbp (caller's)    |   0(%rbp)   <- pushed by `push %rbp`;  %rbp points here
 +--------------------------+
 | local                    |  -8(%rbp)
 | (padding)                | -16(%rbp)
 | a  (spilled rdi)         | -24(%rbp)
 | b  (spilled rsi)         | -32(%rbp)
 | ...                      |
 | f  (spilled r9)          | -64(%rbp)   <- below %rsp: the RED ZONE (leaf function)
 +--------------------------+
 lower addresses (stack grows this way)
```

Stack-smash anatomy with a canary:

```text
  buf[0..15] | canary | saved rbp | return address
  AAAAAAAAAA | AAAAAA | AAAAAAAAA | AAAAAAAA...    <- strcpy overwrites upward
             ^ checked before `ret`: mismatch -> __stack_chk_fail -> abort
```

```mermaid
sequenceDiagram
    participant C as caller
    participant S as sum7
    C->>C: args 1..6 -> rdi,rsi,rdx,rcx,r8,r9; push 7
    C->>S: call sum7 (push return address)
    S->>S: push rbp; mov rsp,rbp (prologue)
    S->>S: compute; result -> rax
    S->>S: pop rbp (epilogue)
    S-->>C: ret (pop return address)
    C->>C: add $8,rsp (drop stack arg); use rax
```

## 6. Common mistakes

| Mistake | Consequence | Fix |
|---|---|---|
| Believing locals are "zeroed" because a fresh frame often contains zeros | Bugs appear later when the stack is reused | Initialise explicitly |
| Large arrays/structs as locals | Stack overflow (8 MiB on the test machine) | Heap-allocate |
| Deep or unbounded recursion | Segfault on overflow | Iteration with an explicit stack |
| Passing big structs by value | Copies onto the stack (or hidden pointer + copy) | Pass `const T *` |
| Disabling the stack protector "for speed" without measuring | Removes a cheap defence | Keep `-fstack-protector-strong` |
| Reading `-O2` assembly and expecting a 1:1 mapping to source | Confusion | Use `-O0` to learn, Compiler Explorer to compare levels |
| Hand-written assembly that leaves `%rsp` misaligned before `call` | Crashes in SSE code (`movaps`) in the callee | Keep `%rsp` 16-byte aligned at call sites |
| Clobbering callee-saved registers in assembly | Caller's state corrupted | Save/restore `rbx, rbp, r12–r15` |

## 7. Connections

- **Computer Architecture track:** registers, `call`/`ret`, the return-address stack predictor, and `lea` as an arithmetic unit; Intel CET adds a hardware **shadow stack** that also checks return addresses.
- **Compilers track:** register allocation, spilling, frame layout, inlining and tail calls are back-end topics you just saw the output of.
- **OS track:** signal delivery pushes a signal frame on the user stack (beyond the red zone); threads each get their own stack; `ulimit -s` and guard pages turn overflows into segfaults.
- **Security track:** stack buffer overflow → return-oriented programming (ROP) → defences: canaries, NX stack, ASLR, CET/shadow stacks (lesson P4).
- **Python track:** `ctypes`/`cffi` must follow this ABI to call C; mismatched signatures corrupt the stack.
- **Rust track:** `extern "C"` functions use exactly this convention for C interop.

### Where this shows up in my projects

- **compiler-fuzz:** miscompilations found by differential testing frequently live in exactly these back-end areas — register allocation, spilling across calls, argument passing for unusual parameter lists — which is why reading `-O0` vs `-O2` assembly for a reduced test case (as in Step 1) is the standard way to localise a GCC-vs-Clang disagreement to "front end" or "back end".

## 8. Self-check questions

1. In which registers do the first three integer arguments arrive? Where does the seventh go?
2. Why could `sum7` store at `-64(%rbp)` without adjusting `%rsp`?
3. What does `16(%rbp)` hold in `sum7` at `-O0`, and why 16?
4. Why did `caller` compile to `movl $56, %eax` at `-O2`?
5. How does the stack canary detect an overflow, and why does it check *before* `ret`?
6. What does `-fno-omit-frame-pointer` buy you, and what does it cost?

<details>
<summary>Answers</summary>

1. `%rdi`, `%rsi`, `%rdx`. The seventh is pushed on the stack by the caller.
2. It is a leaf function; the ABI's 128-byte red zone below `%rsp` is guaranteed not to be clobbered asynchronously, so leaf functions may use it directly.
3. The seventh argument. `0(%rbp)` is the saved `%rbp`, `8(%rbp)` is the return address pushed by `call`, so the first stack argument is at 16.
4. GCC inlined `sum7` into `caller` and constant-folded (1+2+…+7)×2 = 56.
5. A random value from thread-local storage is placed between local buffers and the saved registers/return address on entry and re-checked before returning; a linear overflow that reaches the return address must first overwrite the canary. It checks before `ret` so control never transfers to an attacker-controlled address.
6. Reliable, cheap stack walking for profilers and crash reports; it costs one register (`%rbp`) and a couple of instructions per call.

</details>

**Argument registers in order — rdi, rsi, rdx, rcx, r8, r9:**

> **"Di-Si-Dx-Cx, Ettu-Onbadhu"** — say it like a chant: "**Di**, **Si**, **D**-x, **C**-x, *ettu* (8), *onbadhu* (9)". (*Ettu* = eight, *onbadhu* = nine in Tamil.)

**Frame layout above `%rbp` — saved rbp, return address, arguments:**

> **"Pazhaya rbp, Thirumbi-po address, appuram Arguments — 'PTA meeting'."** — Old rbp at 0, return address at 8, arguments from 16: a *PTA* meeting.
